# Windows 11 ARM64 portable application

Extract `EEGTrainingGUI-Windows-ARM64.zip` into a writable directory, then
double-click **EEG Training GUI.exe**. Keep the complete directory together.
The launcher and numerical dependencies are native ARM64 CPU binaries; the
app carries its own isolated Python and .NET Desktop runtime. No Python or
developer tools are needed on the destination computer.

Windows needs Microsoft's C++ runtime. If a clean computer reports a missing
DLL, run the included `dependencies/VC_redist.arm64.exe`, then start the app
again. The native window uses Microsoft Edge WebView2. If that component is
unavailable, **Start in browser.cmd** runs the same local GUI in a browser.
**Check installation.cmd** runs the included device self-check.

`ModuleNotFoundError: No module named 'metrics'` indicates an incomplete
application package: `metrics.py` is this project's own file, not a separately
downloaded dependency. The corrected package includes it under `app/metrics.py`.
The builder checks local imports and tests staged imports in an isolated
process so the developer's checkout cannot hide omitted modules.
The bundled window host explicitly loads the .NET desktop assemblies and
adapts pywebview's folder picker to the public WinForms API. These adaptations
are applied to the portable runtime only, without modifying the dependency
cache. Exported ZIPs omit runtime logs, cache files and generated bytecode.

Configuration, training records and datasets live under `app/configs`,
`app/runs` and `app/data`. New experiments write beside those files.
The GUI waits for confirmation before closing a window with active tasks.
On Windows, job objects contain training processes and their descendants;
Stop ends the whole task tree. The EEG channel driver handles a cooperative
stop first, saving its partial experiment and stopping its remote Pi case.
Logs are in `logs/launcher.log` and `app/runs/gui_*.log`.

This build uses CPU execution. Qualcomm NPU/GPU acceleration is not enabled.
Host timings retain their diagnostic labels and are never labeled Pi evidence.
The EEG channels SSH path uses Windows OpenSSH (`ssh` and `scp`) with existing
key authentication. The older Deploy tab's Pi workflow additionally needs
Git for Windows / Git Bash; its preview reports that requirement when missing.
Dataset distribution permissions still apply when sharing a package that
contains research data. A local migration package may include this workspace's
data; CI builds exclude data and run records by default.

## Rebuilding

The builder works on macOS, Linux or Windows. It downloads publisher files
only when they are absent from the cache, verifies the recorded hashes, installs
the locked Windows ARM64 wheels, and compiles the small launcher with Zig.
It does not freeze Python into the GUI executable: training, evaluation and
ONNX export continue to launch an ordinary bundled Python interpreter.

```bash
python -m pip install uv==0.13.7 ziglang==0.17.0
python -m gui.make_windows --uv /path/to/uv --zig /path/to/zig \
  --include-runs --include-data --out dist/windows
```

Omit `--include-runs` and `--include-data` for a program-only distribution.
Active training directories are skipped when taking a model snapshot.
Choose a fresh `--out` on rebuilding: existing packages may already hold new
user experiments, so the builder refuses to overwrite them. `--offline` uses
cached wheels and runtimes. The output includes a ZIP, SHA-256 checksum and
an unpacked portable folder.

`packaging/windows/requirements.in` describes the pinned numerical/GUI
dependencies. `requirements.lock` pins their transitive dependencies and hashes
for CPython 3.13 / Windows ARM64. `runtime-lock.json` records the official
Python, .NET and C++ redistributable URLs and checksums. Keep these updated
together and repeat the device check after changing them.

## Validation boundaries

The builder checks PE architecture for the launcher, Python, .NET host and
every Python extension module. Source tests cover relocation, non-ASCII paths,
runtime configuration, data inclusion, failed process startup, cancellation
and Windows memory units. These checks do not execute Windows binaries when
the builder runs on macOS/Linux.

`python -X utf8 -m gui.windows_start --check`, inside the shipped runtime on
Windows ARM64, verifies native PyTorch forward/backward, stateful ONNX export,
two-channel timed replay, memory collection, GUI routes, directory locking,
child-process cleanup, .NET and WebView2. The manually triggered **Windows
ARM64 app** workflow builds a data-free package and runs that check on a
Windows ARM64 runner. Interactive window appearance and target-device timing
still need inspection on the actual Windows computer.
